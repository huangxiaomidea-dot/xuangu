# 「别落了」微信小程序开发文档

> 一句话定位：出门前点开小程序，AI 结合你的生活规律、星期、出门时间和当天实际情况（天气、场景、时长），一秒告诉你**该带什么、别落下什么**。

- 文档版本：v1.1（AI 后端改为 Provider 抽象，MVP 使用国内免费模型）
- 状态：待评审 / 可直接进入开发
- 适用团队规模：1 前端 + 1 后端（可由 1 人全栈完成 MVP）

## 1. 产品定位与核心场景

### 1.1 要解决的问题

「出门忘带东西」是高频、低价值感但高痛感的问题：忘带钥匙要等锁匠，忘带伞要淋雨，忘带充电宝要焦虑一整天，周三忘带游泳卡就白跑一趟。

现有方案的问题：
- **待办 App**：需要手动录入，出门时根本想不起来打开。
- **固定清单**：不区分场景，周一上班和周六出游用同一张清单，很快就被忽略。
- **备忘录**：静态文本，不会因为「今天下雨」「今天要加班」而变化。

### 1.2 「别落了」的差异点

| 维度 | 传统清单 App | 别落了 |
|---|---|---|
| 触发方式 | 用户主动想起 | 出门前一键，2 秒出结果 |
| 清单来源 | 手动维护 | AI 生成 + 用户微调 |
| 是否考虑时间 | 否 | 星期几、出门时间、预计时长 |
| 是否考虑天气 | 否 | 是（温度、降水、风力、紫外线） |
| 是否学习习惯 | 否 | 是（每次勾选/忽略都会回流训练画像） |
| 输出形态 | 一长串待办 | 分级卡片：必带 / 建议带 / 可忽略 + 一句话理由 |

### 1.3 典型场景

| 场景 | 上下文 | 期望输出（示例） |
|---|---|---|
| 工作日早晨通勤 | 周二 08:15，晴转雷阵雨，地铁 | 必带：钥匙、手机、工牌；建议：折叠伞（下午 60% 降雨）、充电宝 |
| 周三晚游泳 | 周三 19:00，室内，2 小时 | 必带：泳镜、泳帽、门禁卡；建议：拖鞋、洗漱包（你上次落下过） |
| 周末带娃出游 | 周六 09:30，户外 6 小时，32℃ | 必带：水杯、防晒霜、湿巾、纸尿裤；建议：遮阳帽、备用衣物 |
| 临时出差 | 周四 06:40，异地 2 天 | 必带：身份证、充电器、笔电；建议：换洗衣物、常用药 |
| 看病 | 任意，医院 | 必带：医保卡、身份证、既往病历、现金 |

## 2. 用户流程

### 2.1 主流程（出门检查）

```
打开小程序
    │
    ├─ 首屏立即展示：一个巨大的「我要出门」按钮 + 当前时间/星期/天气
    │
    ▼
点击「我要出门」
    │
    ├─ [0ms]   本地规则引擎 + 上次同场景缓存 → 骨架清单立即渲染（不等网络）
    ├─ [300ms] 请求后端，携带上下文（时间/星期/位置粗粒度/最近一次场景）
    ├─ [~1.5s] AI 返回精修清单 → 平滑替换骨架，带高亮动画标出「新增/变化项」
    │
    ▼
清单页
    │
    ├─ 用户逐项勾选（勾选 = 已带）
    ├─ 长按某项 → 「今天不需要」/「以后别再提醒」
    ├─ 顶部可切换场景（上班/健身/出差/接娃/…）→ 触发重算
    ├─ 底部可调「预计出门时长」「是否会回家」→ 触发重算
    │
    ▼
点击「出发」
    │
    └─ 生成一次出门记录 → 反馈回流 → 更新用户画像
```

**关键设计原则：出门前的用户没有耐心。** 首屏到可用清单必须 ≤ 1 秒（走本地缓存），AI 精修结果是「渐进增强」，不是阻塞项。

### 2.2 首次使用（冷启动）流程

新用户没有任何历史数据，靠三步 30 秒建立初始画像：

1. **选身份标签**（多选）：上班族 / 学生 / 带娃家长 / 经常出差 / 健身 / 开车 / 骑车通勤
2. **选常带物品**（从预置 30 项里勾）：钥匙、手机、钱包、工牌、耳机、水杯、伞、充电宝……
3. **填固定规律**（可跳过）：例如「周三晚上游泳」「周一到周五 8:30 上班」

完成后立刻可用；后续通过使用反馈持续优化，不再打断用户。

## 3. 功能规格

### 3.1 MVP 范围（P0，必须有）

| ID | 功能 | 说明 |
|---|---|---|
| F-01 | 一键出门检查 | 首页大按钮，点击生成清单 |
| F-02 | 场景选择 | 预置场景 + 自定义场景，默认按时间/星期智能预选 |
| F-03 | 出门参数 | 出门时间（默认当前）、预计时长（<2h / 半天 / 全天 / 过夜）、是否回家、交通方式 |
| F-04 | AI 清单生成 | 分级输出：必带 / 建议带 / 可选，每项带一句理由 |
| F-05 | 物品库 | 用户可增删改自己的物品，支持分类和标签 |
| F-06 | 勾选与反馈 | 勾选已带、标记不需要，数据回流 |
| F-07 | 天气接入 | 城市级天气（温度、降水概率、风力、紫外线） |
| F-08 | 微信登录 | 静默登录建立用户，不强制授权头像昵称 |

### 3.2 P1（重要，MVP 后 2 周内）

| ID | 功能 | 说明 |
|---|---|---|
| F-09 | 规律管理 | 用户显式配置「周三晚游泳」这类周期规则 |
| F-10 | 习惯学习 | 从历史反馈自动挖掘规律，向用户确认后生效 |
| F-11 | 出门提醒 | 订阅消息，在常规出门时间前 15 分钟推送 |
| F-12 | 历史记录 | 查看过去的出门清单，一键「照上次再来一遍」 |
| F-13 | 落东西复盘 | 「我落了东西」按钮，记录后针对性提高该物品权重 |

### 3.3 P2（增强）

| ID | 功能 | 说明 |
|---|---|---|
| F-14 | 清单模板分享 | 生成海报 / 分享给家人（出差清单、带娃清单） |
| F-15 | 日历联动 | 用户手动录入当日行程标签（会议/面试/体检） |
| F-16 | 多人场景 | 「一家三口出门」，按成员维度合并清单 |
| F-17 | 语音输入 | 「今天要去医院」一句话生成清单 |

### 3.4 明确不做（划边界）

- ❌ 不做 IoT / 蓝牙防丢器联动（硬件成本与体验闭环不成立）
- ❌ 不做通用待办清单（会稀释「出门」这个核心场景）
- ❌ 不读取用户微信聊天/日历/通讯录（合规风险与信任成本过高）
- ❌ 不做持续后台定位（只在用户点击时获取一次粗粒度位置）

## 4. 信息架构与页面设计

### 4.1 页面结构

```
pages/
├── index/            首页 —— 出门按钮 + 天气 + 场景快捷入口
├── checklist/        清单页 —— 分级清单、勾选、参数调整
├── items/            物品库 —— 我的物品，分类管理
├── routine/          我的规律 —— 周期规则配置、AI 发现的规律确认
├── history/          出门记录 —— 历史清单、落东西记录
└── profile/          我的 —— 身份标签、提醒设置、隐私设置
```

### 4.2 首页布局（核心页，决定留存）

```
┌────────────────────────────────┐
│  周二 8:15        ☀️→🌧 22-29℃  │   ← 时间/星期/天气（一眼可见的上下文）
│  下午 60% 概率有雷阵雨            │
├────────────────────────────────┤
│                                │
│      ┌──────────────────┐      │
│      │                  │      │
│      │    我 要 出 门     │      │   ← 直径占屏宽 60% 的主按钮
│      │                  │      │      单手拇指可达区域
│      └──────────────────┘      │
│                                │
├────────────────────────────────┤
│  常用场景                        │
│  [ 🏢 上班 ] [ 🏊 游泳 ] [ 🛒 买菜 ]│   ← 跳过场景选择，直接出清单
├────────────────────────────────┤
│  💡 今天是周三，你通常晚上去游泳     │   ← 规律提示，点击直接切换场景
└────────────────────────────────┘
```

### 4.3 清单页布局

```
┌────────────────────────────────┐
│ ← 上班  ▾     8:15出门 · 全天 ▾  │  ← 场景与参数可即时改，改则重算
├────────────────────────────────┤
│ 🔴 必带 (3)                     │
│ ☐ 钥匙                          │
│ ☐ 手机                          │
│ ☐ 工牌      你上周三落下过        │
├────────────────────────────────┤
│ 🟡 建议带 (2)                    │
│ ☐ 折叠伞    下午 60% 概率雷阵雨    │
│ ☐ 充电宝    今天预计外出 9 小时    │
├────────────────────────────────┤
│ ⚪ 可选 (2)     ▾ 展开            │
├────────────────────────────────┤
│        [   出  发   ]           │  ← 提交反馈，收起小程序
└────────────────────────────────┘
```

**交互细节：**
- 每项右侧的灰色小字是「理由」，是 AI 输出的核心价值，不可省略。
- 长按弹出：`今天不需要` / `永久移除` / `提到必带`。
- 已勾选项自动置灰下沉，减少视觉噪音。
- AI 结果替换骨架清单时，新增项做一次 300ms 的高亮闪烁，让用户感知到「AI 想到了我没想到的」。

## 5. 数据模型

### 5.1 ER 概览

```
user 1──n item          用户的物品库
user 1──n routine       用户的周期规律
user 1──n outing        每次出门记录
outing 1──n outing_item 该次清单的每一项（含 AI 推荐结果与用户反馈）
user 1──n scene         场景（含预置与自定义）
```

### 5.2 表结构（PostgreSQL）

```sql
-- 用户
CREATE TABLE app_user (
    id              BIGSERIAL PRIMARY KEY,
    openid          VARCHAR(64) UNIQUE NOT NULL,
    unionid         VARCHAR(64),
    nickname        VARCHAR(64),                    -- 可为空，不强制授权
    tags            JSONB DEFAULT '[]',             -- ["上班族","带娃","开车"]
    city            VARCHAR(32),                    -- 城市级，不存精确坐标
    timezone        VARCHAR(32) DEFAULT 'Asia/Shanghai',
    created_at      TIMESTAMPTZ DEFAULT now(),
    updated_at      TIMESTAMPTZ DEFAULT now()
);

-- 场景（系统预置 user_id = NULL，用户自定义则填 user_id）
CREATE TABLE scene (
    id              BIGSERIAL PRIMARY KEY,
    user_id         BIGINT REFERENCES app_user(id) ON DELETE CASCADE,
    code            VARCHAR(32) NOT NULL,           -- work / gym / travel / kids / hospital
    name            VARCHAR(32) NOT NULL,
    icon            VARCHAR(16),
    is_preset       BOOLEAN DEFAULT false,
    sort_order      INT DEFAULT 0
);

-- 物品库
CREATE TABLE item (
    id              BIGSERIAL PRIMARY KEY,
    user_id         BIGINT NOT NULL REFERENCES app_user(id) ON DELETE CASCADE,
    name            VARCHAR(64) NOT NULL,
    category        VARCHAR(32),                    -- 证件/电子/衣物/健康/育儿/运动/其他
    -- 基础权重：用户手动置顶的必带项设为 1.0
    base_weight     NUMERIC(3,2) DEFAULT 0.50,
    -- 场景绑定：{"work": 0.9, "gym": 0.1}
    scene_weights   JSONB DEFAULT '{}',
    -- 条件触发：{"rain_prob_gte": 0.4} / {"temp_lte": 5} / {"duration_gte_hours": 6}
    conditions      JSONB DEFAULT '{}',
    is_archived     BOOLEAN DEFAULT false,
    created_at      TIMESTAMPTZ DEFAULT now(),
    UNIQUE (user_id, name)
);
CREATE INDEX idx_item_user ON item(user_id) WHERE is_archived = false;

-- 周期规律（用户显式配置 或 AI 挖掘后用户确认）
CREATE TABLE routine (
    id              BIGSERIAL PRIMARY KEY,
    user_id         BIGINT NOT NULL REFERENCES app_user(id) ON DELETE CASCADE,
    name            VARCHAR(64) NOT NULL,           -- "周三晚游泳"
    scene_code      VARCHAR(32),
    weekdays        SMALLINT[] NOT NULL,            -- {1,3,5}，1=周一
    start_minute    SMALLINT,                       -- 一天中的第 N 分钟，1140 = 19:00
    end_minute      SMALLINT,
    item_ids        BIGINT[] DEFAULT '{}',
    source          VARCHAR(16) DEFAULT 'user',     -- user / discovered
    confidence      NUMERIC(3,2),                   -- AI 挖掘时的置信度
    is_active       BOOLEAN DEFAULT true,
    created_at      TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX idx_routine_user_active ON routine(user_id) WHERE is_active = true;

-- 出门记录
CREATE TABLE outing (
    id              BIGSERIAL PRIMARY KEY,
    user_id         BIGINT NOT NULL REFERENCES app_user(id) ON DELETE CASCADE,
    scene_code      VARCHAR(32),
    depart_at       TIMESTAMPTZ NOT NULL,
    weekday         SMALLINT NOT NULL,              -- 冗余，便于统计
    minute_of_day   SMALLINT NOT NULL,              -- 冗余
    duration_bucket VARCHAR(16),                    -- short/half_day/full_day/overnight
    transport       VARCHAR(16),                    -- walk/bike/metro/car/train/plane
    will_return     BOOLEAN DEFAULT true,
    weather         JSONB,                          -- 生成时的天气快照
    generated_by    VARCHAR(16),                    -- ai / rule / cache
    latency_ms      INT,
    created_at      TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX idx_outing_user_time ON outing(user_id, depart_at DESC);

-- 清单项 + 反馈（核心训练数据）
CREATE TABLE outing_item (
    id              BIGSERIAL PRIMARY KEY,
    outing_id       BIGINT NOT NULL REFERENCES outing(id) ON DELETE CASCADE,
    item_id         BIGINT REFERENCES item(id) ON DELETE SET NULL,
    item_name       VARCHAR(64) NOT NULL,           -- 冗余快照，防物品被删
    level           VARCHAR(16) NOT NULL,           -- must / suggest / optional
    reason          VARCHAR(128),
    -- 用户反馈
    checked         BOOLEAN DEFAULT false,          -- 勾了 = 带了
    dismissed       BOOLEAN DEFAULT false,          -- 标记今天不需要
    forgotten       BOOLEAN DEFAULT false,          -- 事后回来标记「落下了」
    UNIQUE (outing_id, item_name)
);
CREATE INDEX idx_outing_item_outing ON outing_item(outing_id);

-- 天气缓存（按城市+小时，避免重复调外部 API）
CREATE TABLE weather_cache (
    city            VARCHAR(32) NOT NULL,
    hour_bucket     TIMESTAMPTZ NOT NULL,
    payload         JSONB NOT NULL,
    PRIMARY KEY (city, hour_bucket)
);
```

### 5.3 用户画像视图（供 AI 使用）

不额外建表，用物化视图按天刷新，作为 Prompt 的稳定输入：

```sql
CREATE MATERIALIZED VIEW user_item_stats AS
SELECT
    o.user_id,
    oi.item_name,
    o.scene_code,
    o.weekday,
    COUNT(*)                                            AS shown_count,
    SUM(CASE WHEN oi.checked   THEN 1 ELSE 0 END)       AS taken_count,
    SUM(CASE WHEN oi.dismissed THEN 1 ELSE 0 END)       AS dismissed_count,
    SUM(CASE WHEN oi.forgotten THEN 1 ELSE 0 END)       AS forgotten_count,
    ROUND(SUM(CASE WHEN oi.checked THEN 1 ELSE 0 END)::numeric
          / NULLIF(COUNT(*), 0), 2)                     AS take_rate
FROM outing o
JOIN outing_item oi ON oi.outing_id = o.id
WHERE o.created_at > now() - INTERVAL '180 days'
GROUP BY o.user_id, oi.item_name, o.scene_code, o.weekday;

CREATE UNIQUE INDEX ON user_item_stats (user_id, item_name, scene_code, weekday);
```

## 6. 后端 API 设计

统一前缀 `/api/v1`，鉴权用自签 JWT（由 `wx.login` 的 code 换取 openid 后签发），放在 `Authorization: Bearer <token>`。

### 6.1 接口清单

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/auth/login` | 用 `code` 换 token |
| POST | `/checklists:generate` | **核心接口**：生成出门清单 |
| POST | `/checklists/{id}/feedback` | 提交勾选/忽略反馈 |
| POST | `/checklists/{id}/forgotten` | 事后标记「落了什么」 |
| GET | `/items` / POST / PATCH / DELETE | 物品库 CRUD |
| GET | `/routines` / POST / PATCH / DELETE | 规律 CRUD |
| GET | `/routines/discovered` | AI 挖掘出的、待用户确认的规律 |
| GET | `/outings` | 历史记录（分页） |
| GET | `/context` | 首页上下文：天气 + 当前建议场景 + 规律提示 |

### 6.2 核心接口详情

**POST `/api/v1/checklists:generate`**

请求：

```json
{
  "scene_code": "work",
  "depart_at": "2026-08-18T08:15:00+08:00",
  "duration_bucket": "full_day",
  "transport": "metro",
  "will_return": true,
  "city": "杭州",
  "note": "下午有客户会议",
  "client_cache_key": "work-2-morning"
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `scene_code` | 否 | 不传则由服务端按时间+星期+规律推断 |
| `depart_at` | 否 | 默认服务端当前时间 |
| `duration_bucket` | 否 | `short`(<2h) / `half_day` / `full_day` / `overnight` |
| `transport` | 否 | 影响随身重量与是否需要充电宝、雨具 |
| `will_return` | 否 | 影响「是否需要带备用衣物/钥匙」 |
| `city` | 否 | 城市名，用于天气；不传则用用户档案里的城市 |
| `note` | 否 | 自由文本，用户临时补充（AI 会重点参考） |

响应：

```json
{
  "outing_id": 90183,
  "scene": { "code": "work", "name": "上班" },
  "generated_by": "ai",
  "latency_ms": 1420,
  "context_summary": "周二 8:15 出门，杭州 22-29℃，下午 60% 概率雷阵雨，预计外出一整天",
  "groups": [
    {
      "level": "must",
      "items": [
        { "item_id": 11, "name": "钥匙",  "reason": "每次出门都需要" },
        { "item_id": 12, "name": "手机",  "reason": "每次出门都需要" },
        { "item_id": 18, "name": "工牌",  "reason": "你上周三落下过一次" }
      ]
    },
    {
      "level": "suggest",
      "items": [

## 7. AI 推理层设计

### 7.1 架构：规则引擎 + LLM 混合

纯 LLM 有三个问题：**慢**（1–3s）、**贵**、**不稳定**（同样输入可能给出不同清单）。纯规则的问题是：不会推理「今天 32℃ 带娃户外 6 小时 → 要带备用衣物」这类组合场景。

因此采用两层：

```
        ┌─────────────────────────────────────────┐
用户请求 →│  L1 规则引擎（本地/服务端，<50ms）          │→ 骨架清单（立即返回）
        │  · base_weight ≥ 0.9 的固定必带项         │
        │  · 命中 routine 的绑定物品                 │
        │  · 命中 conditions 的条件物品（雨/冷/长时）  │
        └─────────────────────────────────────────┘
                        │  规则结果 + 统计画像 + 天气 + 用户备注
                        ▼
        ┌─────────────────────────────────────────┐
        │  L2 LLM 精修（~1.5s，模型可换）             │→ 最终清单（渐进替换）
        │  · 分级排序（must/suggest/optional）        │
        │  · 生成每项「一句话理由」                    │
        │  · 补充规则想不到的组合项                    │
        │  · 剔除明显冗余（如「不回家」时的家用物品）    │
        └─────────────────────────────────────────┘
```

L1 的结果**永远先返回**给客户端（HTTP 立即响应 or SSE 第一帧），L2 完成后通过第二帧 / 轮询补充。这样即使 LLM 超时或欠费，产品仍然可用。

### 7.2 模型选择与 Provider 抽象

**MVP 阶段用国内免费额度跑通，等评测集有数据后再决定要不要升级。** 本任务的难点不在推理能力，而在「理由文案要短、要有信息量、要像人话」，这一点上免费档模型和旗舰模型的差距远小于跑分差距——不要在没有评测数据前就锁定模型。

| 平台 | 免费额度 | 推荐模型 | 适配度 |
|---|---|---|---|
| **智谱 GLM** | Flash 系列长期免费 | `glm-4-flash` | ⭐⭐⭐⭐⭐ 中文语感好、延迟低，**MVP 首选** |
| **阿里百炼（通义）** | 新用户百万级 token 试用 | `qwen-flash` / `qwen-turbo` | ⭐⭐⭐⭐⭐ 稳定性最好，额度用尽后单价也极低 |
| **硅基流动 SiliconFlow** | 部分小模型免费 + 注册赠额度 | `Qwen/Qwen2.5-7B-Instruct` | ⭐⭐⭐⭐ 一个 key 切十几个模型，**适合选型对比** |
| **火山引擎豆包** | 每模型有免费额度 | `doubao-lite` | ⭐⭐⭐⭐ 并发和稳定性好 |
| **DeepSeek** | 非免费但极便宜 | `deepseek-chat` | ⭐⭐⭐⭐ 本项目用量下月成本个位数元 |
| **Claude** | 付费 | `claude-opus-5` | ⭐⭐⭐⭐⭐ 文案质量上限最高，作为**升级路径**保留 |

> 各家免费政策变动频繁，接入前务必到官网 pricing 页确认当前规则。

**硬性要求：AI 调用必须走 Provider 抽象层。** 上述平台除 Claude 外都兼容 OpenAI SDK 协议，切换只需改 `base_url` + `model`，因此代码里不允许出现任何厂商专属调用散落在业务逻辑中。选型结论必须来自 15.2 的 30 组评测集横向跑分，不能凭感觉。

**升级触发条件**（满足任一即评估换模型）：

- 评测集「理由有效性」低于 80%，且调 Prompt 无法改善
- 清单项勾选率（`checklist.take_rate`）持续低于 0.4
- 免费额度的 QPS 限制导致 `ai.fallback_rate` > 5%

### 7.3 Prompt 结构（为缓存而设计）

主流大模型的上下文缓存都是**前缀匹配**：前缀里任何一个字节变化都会让后面全部失效（DeepSeek 自动命中、通义/豆包需显式开启 context cache、Claude 用 `cache_control` 打断点）。因此无论用哪家，都严格按「稳定 → 半稳定 → 易变」的顺序组织：

```
[1] system（全局稳定，所有用户共享）        ← 命中率最高
    · 角色定义、分级规则、输出规范、文案风格

[2] user 第一段（每用户稳定，按天变化）      ← 按用户缓存
    · 用户身份标签、物品库全量、规律列表、历史统计摘要

[3] user 最后一段（本次请求，每次都变）      ← 不参与缓存
    · 当前时间/星期/天气/场景/时长/交通/用户备注
```

[1]+[2] 通常在 1500–3000 token。即使所选平台完全不支持缓存，这个顺序也不吃亏——它同时让 Prompt 结构清晰、便于按用户维度做 A/B。

⚠️ **绝对不要**把「当前时间」拼进 system prompt —— 那会让每一次请求的缓存全部失效。这是本项目最容易踩的性能坑：功能完全正常，成本悄悄翻数倍，只能靠 12.4 的 `ai.cache_read_ratio` 指标发现。

SYSTEM_PROMPT = """你是「别落了」小程序的出门清单助手。用户在出门前打开小程序，你要在他迈出家门前告诉他该带什么。

- 用户标记过 forgotten 的物品，同场景下优先提升到 must，并在理由中提示。

只输出 JSON，不要任何解释性文字。输出格式：
{"context_summary": "...", "groups": [{"level": "must|suggest|optional",
 "items": [{"name": "...", "reason": "..."}]}], "tips": "..."}"""

```python
# app/ai/checklist.py
import json
import logging
import os
from app.ai.provider import get_client
from app.ai.prompts import SYSTEM_PROMPT

logger = logging.getLogger(__name__)
LEVELS = {"must", "suggest", "optional"}


def _validate(data: dict) -> dict:
    """免费档模型的 JSON mode 只保证「是合法 JSON」，不保证字段结构，必须自行校验。"""
    groups = data.get("groups")
    if not isinstance(groups, list) or not groups:
        raise ValueError("groups 缺失或为空")
    for g in groups:
        if g.get("level") not in LEVELS or not isinstance(g.get("items"), list):
            raise ValueError(f"分组结构非法: {g!r}")
        for it in g["items"]:
            if not it.get("name"):
                raise ValueError(f"物品缺少 name: {it!r}")
            it["reason"] = (it.get("reason") or "")[:20]
    return data


def _extract_json(text: str) -> dict:
    """小参数模型偶尔会把 JSON 包在 ```json 围栏里或多写一句解释。"""
    text = text.strip()
    if text.startswith("```"):
        text = text.split("```")[1].lstrip("json").strip()
    start, end = text.find("{"), text.rfind("}")
    return json.loads(text[start:end + 1])


def generate_checklist(profile: dict, ctx: dict, rule_draft: list[dict],
                       provider: str = os.getenv("AI_PROVIDER", "glm")) -> dict:
    client, model = get_client(provider)
    resp = client.chat.completions.create(
        model=model,
        messages=[
            {"role": "system", "content": SYSTEM_PROMPT},          # [1] 稳定
            {"role": "user", "content": (
                f"<user_profile>\n{json.dumps(profile, ensure_ascii=False, sort_keys=True)}\n</user_profile>"  # [2] 半稳定
                f"\n<today>\n{json.dumps(ctx, ensure_ascii=False, sort_keys=True)}\n</today>"                  # [3] 易变
                f"\n<rule_draft>\n{json.dumps(rule_draft, ensure_ascii=False)}\n</rule_draft>"
                "\n请基于 rule_draft 精修，可增删，输出最终清单 JSON。"
            )},
        ],
        response_format={"type": "json_object"},
        max_tokens=1500,
        timeout=float(os.getenv("AI_TIMEOUT_SECONDS", "2.5")),
    )

    result = _validate(_extract_json(resp.choices[0].message.content))

    u = resp.usage
    log_usage(provider=provider, model=model,
              prompt_tokens=u.prompt_tokens, completion_tokens=u.completion_tokens,
              cached_tokens=getattr(getattr(u, "prompt_tokens_details", None), "cached_tokens", 0))
    return result
```

> **`response_format` 不等于 schema 约束。** 国内多数模型的 JSON mode 只保证输出是合法 JSON，不保证字段符合你的结构，因此 `_validate()` 是必需的，不是防御性冗余。若后续升级到支持严格结构化输出的模型（如 Claude 的 `output_config.format`），可在 Provider 层内部改用原生 schema 约束，`_validate()` 保留作为兜底。

## 8. 习惯学习机制

### 8.1 三层学习，从轻到重

**第 1 层：统计权重（实时，无需模型）**

每次 feedback 落库后，异步更新 `user_item_stats`。核心指标：

```
take_rate(item, scene, weekday) = taken_count / shown_count
```

- `take_rate ≥ 0.85` 且 `shown_count ≥ 5` → 自动提升该物品在该场景的 `scene_weights` 至 0.9（进 must 候选）
- `take_rate ≤ 0.15` 且 `shown_count ≥ 8` → 降权至 0.1（沉到 optional 或不再展示）
- `forgotten_count ≥ 1` → 该物品在同场景下未来 30 天内强制进 must，理由带「你上次落下过」

**第 2 层：周期规律挖掘（每周离线跑一次）**

用简单频次统计找周期性，不需要 LLM：

```python
# 伪代码：找出「某物品在某星期几的携带率显著高于其他日子」
for item in user_items:
    baseline = take_rate(item, scene=None, weekday=None)
    for wd in range(1, 8):
        rate = take_rate(item, weekday=wd)
        n = shown_count(item, weekday=wd)
        # 至少 4 次观测，且高出基线 40 个百分点
        if n >= 4 and rate - baseline > 0.4:
            propose_routine(item, weekday=wd, confidence=rate)
```

挖掘出的规律**不直接生效**，进入 `routine` 表 `source='discovered'`，在「我的规律」页展示为待确认卡片：

> 💡 发现规律：你最近 5 个周三都带了泳镜和泳帽，要设为固定规律吗？ [ 是 ] [ 不用 ]

用户确认后 `is_active=true`。这一步很关键——**未经确认的自动规则会让用户感觉失控**。

**第 3 层：LLM 语义理解（按需）**

当用户在 `note` 里写自由文本（「今天去医院复查」「明天飞北京两天」），由 LLM 直接理解并映射到场景与物品，不入规则表，只作用于当次。

### 8.2 冷启动策略

新用户前 5 次出门，清单几乎完全来自：预置模板（按身份标签）+ 天气条件 + 用户初始勾选的常带物品。此阶段刻意保持清单**短**（must ≤ 4 项），避免第一印象是「一堆没用的东西」。

第 5 次之后统计量足够，开始个性化。

## 10. 隐私与合规

### 10.1 数据最小化

| 数据 | 是否收集 | 说明 |
|---|---|---|
| openid | ✅ | 用户唯一标识，必需 |
| 昵称/头像 | ❌ | 不需要 |
| 精确定位 | ❌ | 只保留城市名 |
| 物品名称 | ✅ | 用户自填，是核心数据 |
| 出门时间/星期 | ✅ | 规律学习必需 |
| 通讯录/相册/日历 | ❌ | 完全不申请 |

### 10.2 必做项

1. **小程序隐私协议**：在微信后台配置《用户隐私保护指引》，声明收集 openid、位置（城市级）、用户自填内容。
2. **`wx.requirePrivacyAuthorize`**：基础库 2.32.3+ 起，调用位置等接口前必须完成隐私授权弹窗。
3. **数据出境说明**：MVP 使用境内大模型（智谱/通义等），无数据出境问题。若后续切到境外模型（如 Claude），需在隐私政策中明确告知「用户填写的物品与场景信息会用于生成清单，可能经由境外 AI 服务处理」，并提供关闭 AI 功能的开关（关闭后退化为纯规则引擎）。**这一条必须在上线前与法务确认。**
4. **脱敏**：发给 LLM 的 payload 中不包含 openid、不包含任何联系方式；物品名如包含疑似敏感词（药品名、病历），提供「本地处理」开关。
5. **数据删除**：「我的 → 设置 → 删除我的全部数据」，物理删除并在 7 天内清理备份。

### 11.1 技术栈

| 层 | 选型 | 理由 |
|---|---|---|

| 缓存 | Redis | 天气缓存、清单缓存、限流 |
| AI | OpenAI Python SDK (`openai`) + Provider 抽象层 | 国内主流平台均兼容 OpenAI 协议，换厂商只改 base_url + model |
| 部署 | 微信云托管 或 自有 K8s | 云托管省去备案与域名配置，MVP 阶段更快 |
| 监控 | Prometheus + Grafana | 重点看 P95 延迟与缓存命中率 |

## 12. 性能、降级与容错

### 12.1 延迟预算

| 阶段 | 目标 | 手段 |
|---|---|---|
| 小程序冷启动 → 首屏可见 | ≤ 800ms | 分包、Skyline、首屏不请求网络 |
| 点击按钮 → 骨架清单可见 | ≤ 200ms | 本地规则引擎 + `wx.setStorageSync` 缓存 |
| 点击按钮 → AI 清单到达 | P95 ≤ 2.5s | `effort: low`、prompt 缓存、并行取天气 |
| 提交反馈 | 异步，不阻塞 UI | 乐观更新 + 失败重试队列 |

### 12.2 降级链路

```
AI 调用超时(2.5s) / 报错 / 限流
        │
        ├─→ 命中 Redis 中同用户同场景 24h 内的清单？ → 返回，标记 generated_by="cache"
        │
        ├─→ 否 → 返回 L1 规则引擎结果，标记 generated_by="rule"
        │
        └─→ 规则引擎也无结果（极端新用户）→ 返回身份标签对应的预置模板
```

**任何情况下都不返回错误页。** 出门场景下的空白页 = 用户流失。

### 12.3 错误处理要点（后端）

异常要分类处理，不要一把 `except Exception` 兜住——**限流和超时是要计入降级率的正常状态，参数错误则是需要报警的 bug**：

```python
import openai

try:
    result = generate_checklist(profile, ctx, draft)
except openai.RateLimitError:              # 免费额度的 QPS 上限，MVP 阶段最常见
    metrics.incr("ai.rate_limited")
    return fallback_from_cache_or_rules(...)
except openai.APITimeoutError:
    metrics.incr("ai.timeout")
    return fallback_from_cache_or_rules(...)
except openai.APIStatusError as e:
    metrics.incr("ai.api_error", tags={"status": e.status_code})
    logger.error("llm api error", extra={"status": e.status_code, "body": e.response.text[:500]})
    return fallback_from_cache_or_rules(...)
except openai.APIConnectionError:
    metrics.incr("ai.conn_error")
    return fallback_from_cache_or_rules(...)
except (ValueError, json.JSONDecodeError) as e:  # 模型输出结构不合法
    metrics.incr("ai.bad_output")
    logger.warning("llm bad output: %s", e)
    return fallback_from_cache_or_rules(...)
```

**免费额度的 QPS 限制（常见 2–10 QPS）是 MVP 阶段最主要的失败来源**，必须纳入降级链路而不是当异常报警。早高峰 8:00–9:00 是请求尖峰，上线前用压测确认限流时降级路径工作正常。

另外注意：部分平台在内容安全策略触发时会返回 HTTP 200 但 `content` 为空或被替换成拒绝话术。解析前先判空，避免 `content[0]` 抛异常：

```python
content = resp.choices[0].message.content
if not content or not content.strip():
    metrics.incr("ai.empty_output")
    return fallback_from_cache_or_rules(...)
```

对本项目而言这几乎不会触发（出门清单不涉及敏感领域），但代码必须能安全通过。

### 12.4 关键监控指标

| 指标 | 告警阈值 |
|---|---|
| `checklist.generate.p95_latency` | > 3s |
| `ai.cache_read_ratio`（缓存读 token / 总输入 token） | < 0.5（说明前缀被污染了） |
| `ai.fallback_rate` | > 5% |
| `checklist.take_rate`（清单项被勾选比例） | < 0.4（说明推荐质量差） |
| `retention.d7` | — |

其中 `ai.cache_read_ratio` 是最容易悄悄劣化的指标：任何人往 system prompt 里加了一个时间戳，成本会直接翻数倍而功能完全正常，只能靠监控发现。

## 13. 成本估算

### 13.1 MVP 阶段：基本为零

用智谱 GLM Flash（长期免费）或百炼试用额度，**MVP 到 1,000 DAU 之前 AI 侧成本为 0**，唯一的约束是免费额度的 QPS 上限（见 12.3）。此阶段真正的成本是服务器与数据库：微信云托管/云开发的免费额度基本可覆盖，月支出量级在几十元。

### 13.2 升级到付费模型后的量级

按每次生成约 2,300 输入 token（其中 2,000 为可缓存前缀）+ 450 输出 token 估算：

| 模型档位 | 单次成本 | 1,000 DAU 月成本 | 10,000 DAU 月成本 |
|---|---|---|---|
| 国内 Flash/Lite 档（付费部分） | ≈ ¥0.001 | ≈ ¥45 | ≈ ¥450 |
| DeepSeek `deepseek-chat` | ≈ ¥0.002 | ≈ ¥90 | ≈ ¥900 |
| Claude Opus 5（缓存命中） | ≈ ¥0.10 | ≈ ¥4,500 | ≈ ¥45,000 |

> 按人均 1.5 次/天估算。国内平台价格变动频繁，上表为量级参考，接入前以官网 pricing 为准。

结论很直接：**在国内模型档位上，AI 成本可以忽略不计；只有升到 Claude 这一档才需要认真做成本控制。** 因此选型的决策依据应该是评测集上的质量差距是否值这个价钱，而不是「先省钱」。

### 13.3 降本手段（按优先级）

1. **模式固定的日常通勤走纯规则引擎**，只有天气突变 / 场景变化 / 新场景才调 AI（预计可省 50%+）。效果最好且不损失体验，建议 MVP 后立刻做。
2. 同用户同场景同天的重复请求走 Redis 缓存（预计可省 30–40%）。
3. 缩短输出：理由文案限 14 字、清单项限 15 项以内——输出 token 是成本大头，且短清单本身体验更好。
4. 分层调度：高价值场景（出差、带娃、天气突变）用好模型，日常通勤用便宜模型。Provider 抽象层已支持按场景传入不同 provider。

第 1、3 条同时改善体验和成本，优先做；第 4 条等有评测数据后再上。

## 15. 测试与验收标准

### 15.1 功能验收

| 用例 | 预期 |
|---|---|
| 新用户完成引导后首次点击「我要出门」 | ≤ 2.5s 出清单，must 项 ≤ 4 项，无明显无关物品 |
| 下雨天（降水概率 > 40%）点击 | 伞类物品出现在 must 或 suggest，理由包含具体概率数字 |
| 周三 19:00 点击（已配置游泳规律） | 场景自动预选为「游泳」，泳具在 must |
| 断网点击 | 展示上次同场景缓存清单，顶部提示「离线清单」 |
| AI 服务不可用 | 返回规则引擎结果，用户无感知（不出现报错页） |
| 连续两次同场景请求 | 第二次 `cache_read_input_tokens > 0`（缓存生效） |
| 标记某物品「永久移除」 | 后续同场景不再出现 |
| 标记「我落了充电宝」 | 下次同场景充电宝在 must，理由含「上次落下过」 |

### 15.2 AI 质量评估

建立 30 组固定评测集（覆盖：工作日通勤 ×5、雨天 ×4、极端温度 ×4、健身 ×3、出差 ×4、带娃 ×4、看病 ×2、临时场景 ×4），每次改 Prompt 或换模型/effort 档位后回归：

| 指标 | 定义 | 目标 |
|---|---|---|
| 必带准确率 | must 项中人工判定「确实必须」的比例 | ≥ 90% |
| 漏报率 | 人工清单中有但 AI 未给出的关键物品占比 | ≤ 10% |
| 噪音率 | 清单中人工判定「完全不需要」的占比 | ≤ 15% |
| 理由有效性 | 理由包含具体依据（数值/历史/活动）的比例 | ≥ 80% |
| 结构合法率 | 输出符合 JSON Schema 的比例 | 100%（结构化输出保证） |

### 15.3 性能验收

- 首页冷启动 → 可交互：≤ 800ms（微信开发者工具性能面板，中端安卓机）
- `checklists:generate` P95：≤ 2.5s；P99：≤ 4s
- 后端单实例 QPS：≥ 50（规则路径）、≥ 10（AI 路径）

## 16. 未来迭代方向

1. **回家提醒**：反向场景——离开办公室/健身房时提醒「别落下水杯、雨伞、充电器」。这可能比出门场景更高频，因为在外面落东西才是真正的痛点。
2. **物品位置记忆**：「钥匙通常在玄关柜」，配合清单一起提示，减少「知道要带但找不到」的问题。
3. **家庭共享清单**：一个账号下多成员，出门时按谁出门生成不同清单。
4. **旅行打包模式**：从「出门 5 分钟」扩展到「出差前一晚打包」，清单更长、支持分类折叠和打包进度。
5. **主动感知**：结合微信运动步数或用户主动打卡，识别「已出门」状态，用于验证清单是否被真的执行。
